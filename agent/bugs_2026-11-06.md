# P0 — B11: месяц бюджета и добавление дохода

## Что говорил пользователь

Сценарий: 17 сентября, период «до 20-го», то есть бюджет активен за **август** (20.08–19.09).

```text
Неверно
Я ввела доп 10000
Ожидала что тот минус в который я ушла пересчитается
То есть я записала 2200
Ушла в минус 1000
В лимите было по 0 везде
А потом я добавила 10000
Ожидаю увидеть что сейчас 9000 свободно

А он пишет

БАЛАНС · 🔴 Атас
Сегодня
Свободно 0 ₽ ⛔ · Потрачено 18,343 ₽ ⚠️
...
Период (до 20-го · 3 дн.)
Остаток 0 ₽ · Лимит 0 ₽/день

Последние метры, денег нет. Но мы доползём без кредитов!

Тоже жопа показывает нет лимита
```

И сразу после этого:

```text
✅ Готово! Доход увеличен на 10,000₽
💰 Текущий доход: 24,933₽
```

То есть сообщение об успехе есть, а статус не изменился.

Ещё один симптом из того же сценария:

```text
❌ Не удалось сформировать отчёт. Возможно, у тебя ещё нет бюджета на этот месяц.
Нажми /start, чтобы настроить!
```

При этом бюджет есть — просто `limit == 0`.

## Что реально в коде

1. `src/services/budget_service.py:128-139` — `update_budget_field` ищет бюджет по:
   ```python
   month = get_msk_now().strftime("%Y-%m")
   ...
   Budget.month == month
   ```
   То есть **только текущий календарный месяц**.

2. `get_active_budget` (`budget_service.py:11-34`) при `period_start_day > today.day` ищет бюджет **в прошлом месяце**.

3. 17 сентября, старт 20-го:
   - активный бюджет лежит в `2026-08`;
   - `update_budget_field` ищет `2026-09`;
   - строки нет → `if budget:` не срабатывает → **молчаливый no-op**;
   - сообщение «Доход 24 933» считается из старого объекта в памяти, но в БД ничего не уходит.

4. `save_add_income` (`menu.py:2160-2175`) при `free_money > 0` увеличивает `free_money`, но всё равно пишет «Текущий доход». Это вторая, менее злая проблема: текст врёт о том, что изменилось.

5. `evening_flow.py:175-182` при `limit <= 0` показывает `ERR_REPORT_FAILED` с текстом «возможно, нет бюджета». Это ложь: бюджет есть, денег на сегодня нет.

## Что считать исправлением

- Все правки бюджета (`total_income`, `mandatory_payments`, `black_day_fund`, `period_start_day`, `wishlist_*`) идут **по `budget.id` активного бюджета**, а не по календарному месяцу.
- Онбординг с будущим стартом (`today.day < period_start_day`) сохраняет бюджет в месяц, который `get_active_budget` реально найдёт.
- `save_add_income`:
  - `free_money > 0` → увеличивает `free_money`, сообщение «Свободно»;
  - иначе → увеличивает `total_income`, сообщение «Доход»;
  - решить и зафиксировать в ADR, пересчитывается ли `base_daily_limit` (предложение: да, иначе Recovery-триггер врёт).
- Вечерний отчёт при существующем бюджете и `limit == 0` рендерится как перерасход/ноль, а не как «нет бюджета».

## Цифры для теста

Из скриншота:

- `total_income` после добавления: `24 933`;
- `spent_period`: `18 343`;
- `mandatory`: по скриншоту не видно, принять `0`;
- `days_left`: `3`;
- ожидаемый `money_for_life`: `24 933 - 18 343 = 6 590`;
- ожидаемый `plan_today`: `6 590 / 3 = 2 196,67`.

Важно: пользователь ожидала «9 000 свободно», но по цифрам её перерасход был `3 410`, а не `1 000` (14 933 остатка − 18 343 трат). Поэтому корректный ответ бота — около `6 590`, а не `9 000`. **Главный баг не в разнице 9 000/6 590, а в том, что статус не изменился вообще.**

# P0 — B12: план на сегодня, «Свободно» и дни периода

## Пример 1 — «потрачено 9 015, лимит 9 361, а свободно 0»

```text
Не поняла потрачено 9010 а лимит 9300 почему свободно 0

☀️ Доброе утро, бро!

📋 План на сегодня: 9361 ₽/день

📅 Вчера: ты потратил 3669 ₽ из 9361 ₽ — уложился 👌

Красиво. Прогноз — 9361 ₽/день. Так и едем.

БАЛАНС · 🟢 В лимите

Сегодня
Свободно 0 ₽ ⛔ · Потрачено 9,015 ₽ ⚠️
...
Период (до 20-го · 17 дн.)
Остаток 150,134 ₽ · Лимит 8,831 ₽/день

Всё пучком. Лимит комфортный. Продолжай в том же духе!
```

## Что реально в коде

`menu.py:502-511`:

```python
days_left = budget.days_remaining
dl_base = budget.daily_limit
money_for_life = get_money_for_life(budget, spent_period)
dl_pred = get_daily_pred(money_for_life, days_left)
...
remaining_today = max(dl_pred - spent_today, 0)
```

`money_for_life` — это остаток **после** сегодняшних трат. `dl_pred` уже посчитан из этого остатка. Затем из него ещё раз вычитается `spent_today` → **двойное вычитание**.

На цифрах:

```text
Остаток 150 134 ₽
Потрачено сегодня 9 015 ₽
Дней 17 (включая сегодня)

Текущий код:
  dl_pred = 150 134 / 17 = 8 831
  free    = 8 831 - 9 015 = -184 → 0

Правильный план на старте дня:
  plan_today = (150 134 + 9 015) / 17 = 9 361
  free_today = 9 361 - 9 015 = 346
```

То есть «Свободно 0» — ложь. Должно быть `346 ₽`.

## Пример 2 — «остаток дней, должно делиться без сегодня»

```text
Тут прям сильный баг с лимитом где остаток дней
У должно делиться вся сумма на дни без сегодняшнего

БАЛАНС · 🟢 В лимите

Сегодня
Свободно 5,172 ₽ · Потрачено 3,669 ₽
...
Период (до 20-го · 18 дн.)
Остаток 159,149 ₽ · Лимит 8,841 ₽/день

Идём идеально по графику! Прогнозный лимит: 8,841 ₽/день. Жаба спокойна!
```

Здесь в одном экране смешаны три разные величины:

| Число | Что это | Формула |
|-------|---------|---------|
| `8 841` | живой средний остаток | `159 149 / 18` |
| `9 045` | план на старте дня | `(159 149 + 3 669) / 18` |
| `9 361` | план на завтра | `159 149 / 17` |

`days_remaining` считает **включая сегодня** — это верно и закреплено 14 тестами (`test_daily_limit_scenarios.py`). Пользователь ожидает деление на дни **без сегодня** (`159 149 / 17 = 9 361`), потому что «Остаток» уже после сегодняшних трат. Это отдельное продуктовое решение, а не баг в `days_remaining`.

**Принятое решение:** модель A — «план на сегодня» фиксируется на старте дня, «Свободно» = план − траты, «Остаток» — отдельно. Делитель «без сегодня» отдельно не вводим.

## Формула, которую надо реализовать

```python
plan_today = (money_for_life + spent_today) / days_left  # days_left включает сегодня
free_today = max(plan_today - spent_today, 0)
remaining_period = money_for_life
```

Свойство: без recalc `money_for_life + spent_today = const`, поэтому `plan_today` не меняется от каждой новой траты. Это и есть «план зафиксирован утром», без новой колонки в БД.

## Дополнительные баги в этом же экране

### 1. «до 20-го» вместо «до 19-го»

`menu.py:513-514`:

```python
period_end_day = budget.period_start_day or 1
period_end_str = f"{period_end_day}{phrases.PERIOD_DAY_SUFFIX}"
```

Для старта 20-го период заканчивается **19-го** следующего месяца (`get_period_dates`). Надо брать `period_end.day`.

### 2. `_period_total_days` жёстко = 30

`models.py:88-96`:

```python
if start == 1:
    return calendar.monthrange(today.year, today.month)[1]
return 30
```

Период 20.08–19.09 = **31 день**, 20.09–19.10 = 30, 20.02–19.03 = 28/29. `_compute_base_limit` (`budget_service.py:49`) тоже хардкодит 30. Это искажает базовый дневной лимит и зоны.

### 3. «Уложился + притормаживаем»

```text
📅 Вчера: ты потратил 5499 ₽ из 6384 ₽ — уложился 👌
📉 Бро, притормаживаем. Прогноз — 6384 ₽/день.
```

`morning_report.py:165-193` сравнивает вчерашние траты с **сегодняшним** `dl_pred`, а тон выбирает по `pct_pred`. Поэтому «уложился» и «притормаживаем» могут стоять рядом. Это уже B13 (зоны/тон), но проверять вместе с B12, потому что после новой модели план на сегодня и зона периода должны считаться отдельно.

### 4. «Зелёный» при «Свободно 0»

`menu.py:524-535` ставит 🟢 при `pct_pred > 80`, не глядя на `free_today`. После B12 это должно стать невозможным: если `free_today == 0`, зелёного «В лимите» быть не может.

## Что считать исправлением B12

- В статусе:
  - `План на сегодня: 9 361 ₽`
  - `Свободно: 346 ₽ · Потрачено: 9 015 ₽`
  - `Остаток: 150 134 ₽` (отдельная строка)
- «Лимит 8 831/день» либо убрать, либо подписать как «средний на день» и не смешивать со «Свободно».
- `period_end_str` = `period_end.day`.
- `_period_total_days` и `_compute_base_limit` = фактическая длина периода.
- Утренний план и вечерний лимит считаются от той же модели.

## Тесты B12

1. `159 149`, `3 669`, `18 дн.` → `plan_today = 9 045`, `free_today = 5 376`, подпись «до 19-го».
2. `150 134`, `9 015`, `17 дн.` → `plan_today = 9 361`, `free_today = 346` (не `0`).
3. `180 733`, `5 600`, `31 дн.` → проверить план и подпись.
4. Период 20.08–19.09 = 31 день; 20.09–19.10 = 30; 20.02–19.03 = 28/29.
5. Регресс: `days_remaining` по-прежнему включает сегодня; существующие 14 тестов не ломаются.
6. Зелёная зона при `free_today == 0` запрещена.

# B12 — фиксированный «Лимит» (уточнение 2026-11-10)

Пользователь уточнил: в строке `Остаток 99 332 ₽ · Лимит 7 640 ₽/день` число «Лимит» должно быть **планом, зафиксированным утром**, и не меняться от трат в течение дня. По смыслу это «свободно + потрачено».

## Формулы

```text
plan_today    = (money_for_life + spent_today) / days_left
free_today    = max(plan_today - spent_today, 0)
overrun_today = max(spent_today - plan_today, 0)
tomorrow_plan = money_for_life / max(days_left - 1, 1)
```

`plan_today` инвариантен к сегодняшним тратам: `money_for_life + spent_today` не меняется, пока нет пересчёта бюджета.

## Правила отображения

- «Лимит» = `plan_today` **напрямую**, а не `free_today + spent_today`. После обнуления «Свободно» сумма начала бы расти.
- «Свободно» = `free_today`, «Потрачено» = `spent_today`.
- Если `overrun_today > 0` — показывать отдельно: `Свободно 0 ₽ ⛔ · Потрачено 18 343 ₽ · Перерасход 8 982 ₽`, при этом «Лимит» остаётся утренним `9 361 ₽/день`.
- Добавление дохода **пересчитывает** `plan_today` (добавка — не трата).
- «Лимит» не считается как `free + spent` после обнуления свободного.

## Тесты (дополнение)

- `9 045` остаётся `9 045` после траты ещё 1 000 ₽; «Свободно» падает ровно на 1 000 ₽.
- При перерасходе лимит `9 361` не растёт, перерасход `8 982` показывается отдельно.
- Добавка дохода среди дня увеличивает `plan_today`.

# B13/B17 — движок фраз про лимит (уточнение 2026-11-10)

Пользователь: «если он уменьшается — писать цифры в прогнозах; если комфортный — цифры не нужны; но если сегодня вышли за лимит, "Продолжай в том же духе!" не подходит».

## Два фактора выбора фразы

1. **Сжатие относительно базы:** `pct = plan_today / base_daily_limit * 100`, где `base_daily_limit = (доход − обязательные − кубышка) / дни периода`. Это «вся сумма дохода периода / дни», а не `budget.daily_limit` (тот при `free_money > 0` считается от остатка на карте).
2. **Перерасход сегодня:** `overrun_today > 0` запрещает зелёные/расслабленные фразы, даже если `pct` зелёный.

## Прогноз на завтра

- `tomorrow_plan < plan_today` → показывать цифру: «Лимит сожмётся до X».
- `tomorrow_plan >= plan_today` → **никаких** «подрастёт» и цифр; только комфортная фраза.
- В последние 3 дня периода используются финальные фразы (`STATUS_FOOTER_END_*`), прогноз на завтра не показывается.

## Статус

Это B13 (логика выбора) + B17 (тексты). Не входит ни в B11, ни в базовый B12. Записать в `SESSION_PLAN.md` отдельными чеклистами.

# Решения, уже принятые пользователем

1. **Модель A** для денег/дней — принята (см. формулу B12).
2. **Recovery** — выбор A/B отложен, код не менять до решения.
3. **`ADMIN_CHAT_ID`** — добавить отдельно, не возвращая `ADMIN_IDS` из B10; слать traceback + user_id; фраза «😨 Ой-ёёёй, случилась ошибочка!» + «Мы уже оповестили администратора».
4. **Двоеточие** — да, формат `Категория: описание — сумма`.
5. **Месячный отчёт** — да, «сэкономлено» + вопрос про перенос остатка + чистка мёртвых деталей.
6. **B11 — добавление дохода** — ветка `free_money` / `total_income` сохраняется; ответ показывает остаток и план: `✅ Добавлено 10 000 ₽ / 💰 Остаток: 6 590 ₽ / 📅 2 197 ₽/день на 3 дня`.
7. **B11 — `base_daily_limit`** — пересчитывать при изменении дохода / обязательных / кубышки.
8. **B11 — онбординг с будущим стартом** — продолжать текущий период (сохранять в прошлый месяц), в сообщении показывать «Период 20.08–19.09 · осталось 3 дня».
9. **B11 — смена дня старта** — автоматически переносить бюджет в правильный месяц.
10. **B11 — нет активного бюджета** — честная ошибка «Сначала настрой бюджет через /start», без ложного «Готово».
11. **B11 — вечер при `limit = 0`** — честный итог за день; новая фраза для «0 лимит, 0 трат».
12. **B12 — фиксированный «Лимит»** — утренний план, не меняется от трат; перерасход показывается отдельно; добавка дохода пересчитывает план.
13. **B13/B17 — фразы** — сравнивать с `base_daily_limit`; цифры только при сжатии; «подрастёт» не анонсировать; перерасход сегодня блокирует зелёные фразы.
