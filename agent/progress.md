### ✅ B11: месяц бюджета и добавление дохода (2026-11-10)

**Проблема:** `update_budget_field` искал бюджет по календарному `month == now`. При `period_start_day = 20` и сегодняшнем 17-м активный бюджет лежит в прошлом месяце, поэтому правка дохода молча не находила строку — статус не менялся, а пользователь видел «Остаток 0 ₽ · Лимит 0 ₽/день». Тот же корень — онбординг с будущим днём старта. Вечерний отчёт отдельно врал «нет бюджета» при `limit == 0`, хотя бюджет был.

**Решение:**
- `budget_service.py` — `update_budget_field` ищет активный бюджет через `get_active_budget`, обновляет по `id`; при отсутствии бросает `NoActiveBudgetError` (никакого молчаливого no-op).
- `month_for_period_start(start_day, today)` — единая функция «в каком месяце начался период»; онбординг сохраняет бюджет в правильный месяц, смена `period_start_day` автоматически re-anchor'ит `budget.month` и заменяет устаревшую строку в целевом месяце.
- `base_daily_limit` пересчитывается при изменении `total_income`, `mandatory_payments`, `black_day_fund`, `period_start_day`.
- `delete_current_budget` → `delete_active_budget` (по активному id); мёртвая `get_days_remaining` удалена. Добавлен `delete_all_budgets` для полного сброса; оба удаляют строки `RecoveryState` перед бюджетом (обычный FK без cascade — иначе PostgreSQL падает с `IntegrityError`).
- `reset_budget` делает полный сброс бюджета, чтобы старые строки в «неправильном» месяце не воскресали.
- `save_recalc_balance` без активного бюджета показывает `ERR_NO_BUDGET`, а не ложное «Готово».
- Rollover (`keep` / новый период) сохраняет бюджет в месяц через `month_for_period_start`, а не в календарный.
- Вечерний тизер больше не отсекает бюджеты с `daily_limit <= 0`: честный `EVENING_ZERO_NO_MONEY` доходит и через плановую рассылку.
- `menu.py` — все правки бюджета идут через `_apply_budget_update`; при отсутствии бюджета честное `ERR_NO_BUDGET`. Ответ на добавку дохода: `✅ Добавлено 10,000 ₽ / 💰 Остаток: 80,000 ₽ / 📅 N ₽/день на K дн.`, при всё ещё нулевом остатке — `Остаток: 0 ₽ — перерасход ещё не закрыт`.
- `evening_flow.py` / `evening_report.py` — при бюджете с `limit <= 0` показывается честный итог; новая `EVENING_ZERO_NO_MONEY` для «0 лимит, 0 трат».
- Категории в `menu.py` экранируют `name`/`description` через `safe()` — закрыт HTML-injection в `ERR_CATEGORY_EXISTS` / `CATEGORY_CREATED`.

### ✅ B12: план на сегодня / «Свободно» / дни (2026-11-10)

**Проблема:** в статусе `remaining_today = dl_pred - spent_today`, но `dl_pred` уже считался из `money_for_life` — остатка **после** сегодняшних трат. Двойное вычитание: при плане 9 361 и тратах 9 015 «Свободно» становилось 0 вместо 346. Плюс период подписывался днём старта («до 20-го» вместо 19-го), а длина периода для `start_day > 1` была захардкожена 30.

**Решение:**
- `get_plan_today` / `get_free_today` / `get_overrun_today` в `budget_service.py` — единая модель:
  `plan_today = (money_for_life_raw + spent_today) / days_left`, `free_today = max(plan_today - spent_today, 0)`, `overrun_today = max(spent_today - plan_today, 0)`. `get_money_for_life_raw` не клампит остаток в 0, иначе при перерасходе план начинал расти от сегодняшних трат.
- «План на сегодня» фиксирован в течение дня: добавление трат двигает только «Свободно», а не план. Перерасход показывается отдельной строкой `Перерасход N ₽`; «Свободно 0 ⛔» при этом не маскирует план.
- «Остаток» — отдельная строка `Остаток {money_for_life} ₽`; «Лимит N/день» из периода убран, чтобы не смешивать со «Свободно».
- Зелёная зона `🟢 В лимите` и зелёный футер запрещены при `free_today == 0` или `overrun_today > 0`.
- Подпись периода — по `period_end.day` (`до 19-го`).
- `period_dates(month, start_day)` / `period_total_days` в `helpers.py`: единые границы и реальная длина 28–31 день; `Budget.days_remaining` теперь считается от тех же границ (корректно для старта 30/31 в коротких месяцах), `get_period_dates` в `monthly_report.py` делегирует туда же.
- `_build_status` берёт сегодняшние траты из `get_today_expenses_sum`, а не дублирует SQL с другими границами.
- Утренний отчёт и вечерний финализатор считают `plan_today` той же функцией, что и статус (с учётом сегодняшних трат).
- `_compute_base_limit` принимает месяц явно и делит на фактическую длину периода.

**Тесты:** `test_b12_today_plan.py` (25: формулы, инвариантность плана при перерасходе и последнем дне, 31/30/28/29 дней, старт 30/31 в январе–феврале, статус 9 361/346, 9 045/5 376, перерасход 8 982, подпись «до 19-го», фиксированный план после траты, пересчёт плана после дохода, запрет зелёного футера). ### ✅ B22: «Вчера» считается от вчерашнего плана (2026-11-16)

**Проблема:** в утреннем отчёте рядом стояли два разных лимита — `📋 Лимит: 1168 ₽/день` (живой план `dl_pred`) и `📅 Вчера: … из 6666 ₽` (базовый лимит периода `dl_base` = доход ÷ дни). Пользователь видел вчера другое число и воспринимал это как ошибку. Причина: в B13 сравнение «Вчера» перевели с `dl_pred` на `dl_base`, чтобы убрать «уложился + притормаживаем».

**Решение:** вчерашний план восстанавливается без хранения истории:

```python
plan_yesterday = (money_for_life_raw + yesterday_spent + spent_today) / (days_left + 1)
```

`money_for_life_raw` — остаток **сейчас**, поэтому возвращаются траты обоих дней; `spent_today_at_recalc` передавать нельзя — снапшот уже вычтен. `yesterday_ok` и «перебор» считаются от `plan_yesterday`, сравнение идёт по тем же целым числам, что показываются (нет «перебора 0 ₽»). `dl_base` остаётся только для зон. При перерасходе периода `plan_yesterday = 0` — строка пишет «из 0 ₽» (решение пользователя).

**Ограничение:** число совпадает с тем, что видел пользователь, пока между вчерашним утром и отчётом не менялись деньги (добавление дохода, пересчёт лимита). Первый день периода: вчерашние траты относятся к прошлому периоду — на практике путь переката отсекается до утреннего отчёта.

**Тесты:** `test_b22_yesterday_limit.py` (7 тестов). `pytest 548 passed`.

### ✅ M4: месячный отчёт — «Сэкономлено» от доступного лимита (2026-11-18)

**Проблема:** отчёт показывал ярлык «Зона: Зелёная/…», а «Сэкономлено» считал от `total_income − потрачено`, игнорируя обязательные платежи и кубышку. **Решение:**
- База отчёта: `available = total_income − mandatory_payments − black_day_fund` (без клампа в ноль для расчёта, кламп только для решения «нет лимита»).

  - `saved_rounded == 0` → `zero` («Снайперский расчет»), `< 0` → `overrun`.
- Ярлык «Зона: …» удалён из отчёта; зоновые эмодзи в месячном отчёте не рисуются.
- Новые строки: `💵 Доход: X ₽` всегда; `➕ Из них добавлено: +X ₽` при `added_income > 0`.

Обнуляется в `save_budget` (онбординг, rollover, новый период), правки `mandatory`/`black_day` через `update_budget_field` его не трогают.
- Миграция `budgets.added_income REAL/FLOAT NOT NULL DEFAULT 0` + `ALLOWED_COLUMNS` (NOT NULL, чтобы `schema_audit` не ловил дрейф с `Mapped[float]`).
- В деталях отчёта при `black_day_fund > 0` появляется строка `• Кубышка: X ₽`.

### ADR: Recovery≠Recalc≠Savings (2026-09-07) — hard clean Кубышки

## Decision Log (ADR)

### Математические выражения в тратах (2026-07-08)
**Что сделано:** кастомный рекурсивный парсер `_MathParser` в `helpers.py`, который разбирает `500+300 такси` → сумма 800, описание «такси». Без `eval()`.

**Почему не eval:**
`eval("500+300")` — встроенная Python-функция, выполняющая строку как код. Если пользователь напишет `__import__('os').system('rm -rf /')+500`, eval выполнит это. Наш парсер видит только числа и операторы — всё остальное вызывает `_MathParseError`. Безопасность на уровне дизайна, не костыля.

**Архитектура парсера (recursive descent):**
```
parse_expr → parse_term → parse_factor
```
- `parse_expr` обрабатывает `+`/`-` (низший приоритет)
- `parse_term` обрабатывает `*`/`/` (средний приоритет)  
- `parse_factor` обрабатывает числа, скобки, унарный `+`/`-` (высший приоритет)
- Токены: NUMBER / PLUS / MINUS / MUL / DIV / LPAREN / RPAREN / EOF

**Два режима:**
- `_eval_math(text)` — полный разбор, всё строка — математика. Используется в `parse_amount()` (онбординг, редактирование бюджета).
- `_parse_math_prefix(text)` — разбор до первого не-математического символа, возвращает `(total, rest)`. Rest идёт в описание. Используется в `parse_expense_text()`.

**Авто-коррекция (`_preprocess_math`):** три правила, применяются последовательно:
1. Хвостовой оператор → `500+300+` → `500+300`
2. Баланс скобок → `(500+300` → `(500+300)`, `500+300)` → `500+300`
3. Двойные знаки → `500++300` → `500+300`, `500+-300` → `500-300`

**Edge cases (все закрыты):**
- Скобки: `(500+300)*2`, `(500+300)`, `1+1)`, `7+2)-20`
- Унарный +/–: `-5`, `+5`, `5+-3`, `5*-3`
- Научная нотация: `1e5+2e5`, `5e-3`, `2E5`
- Ноль из math: `5-5` → «нулевая сумма», `(7+2)-20` → «отрицательная сумма»
- RecursionError на >950 скобок → MATH_ERROR

**Объём:** ~300 строк ядра (токенизатор + парсер + препроцессор + валидация) + ~120 строк изменений в хендлерах + ~50 строк новых тестов.

### BigTech-паттерны ошибок
- **Pattern 2 (MATH_ERROR):** блок траты, `<code>` для копирования, 3 retry → clear state. Для: деление на ноль, отрицательная/нулевая сумма, неисправимая каша
- **Pattern 1 (was_corrected):** авто-коррекция (скобки, хвостовые операторы, двойные знаки), трата сохраняется, предупреждение + кнопка «✏️ Исправить» (через `exp_edit:{id}`, DRY). Для: лишняя скобка, хвостовой `+`, двойные знаки

### Callback data — только ID
- **Почему:** Telegram лимит 64 байта, защита от инъекций
- **Формат:** `exp_edit:{id}`, `change_cat:{id}`. Никогда сырой текст

### Научная нотация (1e5) — добавлена в NUMBER regex
- **Почему:** `1e5+1e5` до фикса давало 1.0 + мусор как описание (`e5+1e5`)
- **Что:** `\d+(?:[.,]\d+)?(?:[eE][+-]?\d+)?` — в _TOKEN_SPEC и _fallback_first_number

### Zero / negative из math — прямой error вместо fallback
- **Почему:** `7+2)-20` → коррекция `7+2-20` → -11. Раньше выдёргивало первое число (7), теперь честно: «отрицательная сумма»

### current_text_end — возвращает start, а не end
- **Почему:** `1+1)` — RPAREN был включён в «съеденный» диапазон, скобка бесшумно исчезала. Фикс: `tokens[self.pos][2]` вместо `[3]`

### Message Lifecycle Policy («Конституция интерфейса»)
- **Callback:** только `edit_text()`, никогда `delete()`
- **User message:** только `answer()`, не редактировать и не удалять
- **Teaser (22:00):** единственное исключение на delete, с `_last_keyboard.pop()`
- **Rich API:** ручной трекинг `message_id` в `_last_keyboard` (обходит middleware)

### AutoCleanKeyboardMiddleware вместо двух систем
- **Почему:** `_track_keyboard` (TTLCache) и `_save_msg_id` (FSM) не координировались → `TelegramBadRequest` на edit удалённого
- **Решение:** единый middleware, перехватывает `message.answer()`/`edit_text()` на MenuRouter, чистит предыдущую клавиатуру

### Единый _save_expenses_from_parsed_list
- **Почему:** `process_expense` + `handle_text` дублировали ~90 строк
- **Решение:** вынесено в сервис, каждый хендлер — ~20 строк
