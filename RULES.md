# RULES.md — Правила разработки TratoBot (для ИИ-агента)

> Этот файл — свод правил для ИИ-ассистента. Приоритет — над общей эрудицией модели.

## 1. Сессионный ритуал (Session Start)

Перед началом любой рабочей сессии агент **обязательно**:

1. Читает `RULES.md` — освежает правила.
2. Читает `PRD.md` — убеждается, что фичи реализуются согласно документу.
3. Читает `README.md` (раздел **Implementation Status**) — понимает текущее состояние проекта.
4. Читает `progress.md` — понимает статус, что сделано, что в работе, что заблокировано.
5. Говорит: **«Ритуал принят. Статус понял. Поехали.»**

Без выполнения ритуала агент не приступает к задачам.

## 3. Стек технологий

| Компонент | Технология |
|-----------|-----------|
| Язык | Python 3.11+ |
| Telegram API | aiogram 3.x (строго актуальная версия) |
| ORM | SQLAlchemy 2.x (async) |
| База данных | SQLite (dev) + aiosqlite / PostgreSQL 14+ (prod) + asyncpg |
| Планировщик | APScheduler 3.x |
| Конфигурация | Pydantic v2 / Pydantic Settings |
| Линтер/форматтер | Ruff (один инструмент на всё) |
| Тестирование | pytest + pytest-asyncio |

### ❌ Запрещённые инструменты
- `telebot` / `pyTelegramBotAPI` — синхронный, устаревший.
- `aiogram 2.x` — другой синтаксис фильтров и FSM.
- `Black` / `Isort` / `Flake8` / `Autopep8` — всё заменяет Ruff.
- `Celery` / `Redis Queue` — избыточны для 2 крон-задач.

## 5. Разделение на слои (Layer Separation)

```
src/
├── core/          # Конфигурация (config.py), в будущем — phrases.py
├── db/            # Модели SQLAlchemy, database.py, миграции
│   ├── models/    # ORM-модели
│   └── repo/      # (будущее) репозитории
├── services/      # Бизнес-логика. Не импортирует aiogram.
├── bot/           # Слой представления (Telegram)
│   ├── handlers/  # Хендлеры команд, сообщений, коллбэков
│   ├── filters/   # Кастомные фильтры
│   ├── keyboards.py # Фабрики клавиатур
│   ├── scheduler.py # APScheduler
│   └── main.py    # Точка входа
└── utils/         # Вспомогательные утилиты
```

### Правила слоёв
1. **Хендлеры** не содержат бизнес-логики — только вызов сервисов и работу с Telegram API.
2. **Сервисы** не импортируют aiogram — чистая бизнес-логика, работа с моделями БД.
3. **Хендлеры не пишут пользовательские строки** — строки выносятся в `phrases.py` (создать при первой необходимости).
4. **keyboards.py** не хардкодит текст — использует `phrases.py`.
5. **Сервисы не импортируют хендлеры**, хендлеры импортируют сервисы (однонаправленная зависимость).

## 6. Качество кода и тестирование

### Линтинг
- Единственный инструмент: **Ruff** (замена Flake8, Black, isort).
- Строгое следование PEP 8.

### Тестирование
- **pytest + pytest-asyncio** — для критических узлов: парсер расходов, логика FSM, расчёты бюджета.
- Тесты писать для любой новой логики, где есть ветвления или вычисления.

### BigTech Standard: покрытие тестов
Каждый тестируемый модуль обязан покрывать **все** категории сценариев:

| Категория | Что проверять | Примеры |
|-----------|---------------|---------|
| **Happy Path** | Основной функциональный сценарий | "300 кофе" → (300.0, "кофе") |
| **Empty / Null** | Пустые и нулевые входные данные | "", None, пустой список |
| **Boundary** | Граничные значения | ровно 500 символов, 1e12, 0 |
| **Overflow / Limit** | Превышение лимитов | 501 символ, 1e12+, 1000+ элементов |
| **Special Characters** | Спецсимволы | HTML-теги, unicode, эмодзи, управляющие символы |
| **Locale / Format** | Разные форматы ввода | запятая vs точка, unicode минус, ведущие нули |
| **Type / Cast** | Неверные типы | NaN, inf, строка вместо числа |
| **Negative / Edge** | Негативные и неожиданные значения | -100, токены в середине слов, несколько разделителей |
| **Regression** | Регрессия на исправленных багах | Каждый закрытый L/H-файтинг — тест |

**Правило:** при добавлении новой функции или исправлении бага пишется минимум по одному тесту из каждой применимой категории.

### Двухступенчатый рубеж
1. **Локально (pre-commit hook):** Ruff проверяет и форматирует код перед каждым коммитом.
2. **CI (GitHub Actions):** при push/PR в main — Ruff + pytest. Если тесты падают, Railway не деплоит.

## 7. Definition of Done (DoD)

Фича считается завершённой, если:

1. Поведение работает во всех сценариях (happy path + edge cases).
2. Ошибки обрабатываются до пользователя — никаких необработанных исключений.
3. Все пользовательские строки вынесены в `phrases.py`.
4. Есть тесты для критической логики, и они проходят.
5. Нет новых lint-ошибок (Ruff).
6. Код работает на SQLite (dev) и PostgreSQL (prod), если менялась схема.
7. Соблюдено разделение слоёв (п. 5).
8. Соблюдены naming conventions (п. 4).
9. Проверено, что не нарушен характер бота (см. PRD.md раздел «UI и стиль взаимодействия»).

## 8. Правила для агента

### 8.1 Ask User Question перед кодом

Перед любым редактированием существующего кода или созданием нового файла агент **обязан**:

1. Описать проблему: в чём баг или что требуется сделать, со ссылками на код.
2. Предложить решение: какие файлы менять, как именно, почему этот подход.
3. Использовать `Ask User Question` для получения подтверждения или уточнений.
4. Только после одобрения пользователя — приступать к коду.

**Правило действует на любые изменения**, включая баг-фиксы, рефакторинг, новую функциональность. Исключений нет. Даже тривиальные правки проходят через описание + подтверждение.

### 8.2 Архитектурные изменения
Любые изменения, затрагивающие:
- структуру папок,
- выбор новой библиотеки,
- изменения модели данных (новые таблицы/колонки),
- новый внешний API или интеграцию, — **обсуждаются с пользователем до реализации**.

### 8.3 Файлы и коммиты
- **Не создавать файлы без запроса** пользователя.
- **Не делать коммиты** без явной команды пользователя.
- Никогда не коммитить `.env`, credentials, токены.

### 8.4 Стиль кода
- Не добавлять комментарии к коду (если не asked).
- Следовать существующему стилю кода в проекте.
- При реализации новой фичи сначала изучить, как сделаны аналогичные фичи в проекте.

### 8.5 Pre-Push: Database Schema Check

Перед любым пушем в main агент **обязательно** проверяет:

1. Менялась ли модель данных (новые таблицы/колонки в `models.py`)?
2. Если менялась — есть ли соответствующая миграция в `migrate_schema()` (файл `db/database.py`)?
3. Все ли новые идентификаторы (названия таблиц, колонок) добавлены в `ALLOWED_TABLES` / `ALLOWED_COLUMNS` в `database.py`?
4. Совместима ли миграция с PostgreSQL (production) и SQLite (dev)? Типы различаются (`BOOLEAN` vs `INTEGER`, `FLOAT` vs `REAL`).

Если какое-то условие нарушено — **не пушить**, сначала исправить.

### 8.6 Характер бота (Tone of Voice)
Проектируя ответы бота, соблюдать:
- Роль: ироничный напарник, без дистанции.
- Rule of 2 Sentences: максимум 2-3 предложения на сообщение.
- Метафоры: добыча, фундамент, каркас, стройка, навигация.
- **Запрещено:** «финансовый тренер», подхалимаж, угрозы, оценочные суждения.
- Полный гайд — в PRD.md (раздел «UI и стиль взаимодействия»).

## 9. Структура Callback Data

Формат: `action:scope:value` (через двоеточие).

| Пример | Значение |
|--------|----------|
| `set_cat:5:3` | Установить категорию 3 для расхода 5 |
| `exp_page:2` | Страница 2 истории |
| `exp_del:12` | Удалить расход 12 |
| `fix_overdraft:wishlist` | Покрыть овердрафт из хотелки |
| `use_savings` | Использовать кубышку |
