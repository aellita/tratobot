## Bug #1: Дубликат кода process_expense / handle_text (HIGH) ✅ 2026-07-05

В `src/bot/handlers/menu.py` два хендлера содержат ~90 строк почти идентичной логики парсинга и сохранения расходов:
- `process_expense` (FSM-хендлер `AddExpense.waiting_for_amount`)
- `handle_text` (свободный ввод без FSM)

`handle_text` **не имеет** счётчика ретраев (3 попытки → автовыход). Это асимметрия: если пользователь вводит некорректную трату через FSM — получит 3 попытки, через свободный ввод — только одну ошибку и тишину.

**Риск:** любой баг-фикс в одном хендлере надо дублировать в другой. Уже были расхождения.

**Решение:** вынести общую логику (парсинг, валидация, сохранение, round-up, дубликаты) в `_process_and_save_expense(user, text, ...)`, вызвать из обоих хендлеров.

## Bug #2: Две независимые системы отслеживания клавиатур (HIGH) ✅ 2026-07-05

| Система | Где используется | Механизм |
|---------|-----------------|----------|
| `_track_keyboard` / `_cleanup_keyboard` | menu.py (траты, настройки, critical reset) | `TTLCache[chat_id → message_id]`, редактирует `reply_markup=None` |
| `_save_msg_id` / `_cleanup_old_buttons` | Онбординг (`BudgetSetup` states) | FSM-контекст (`state.update_data(msg_id=...)`) |

**Проблема:** Они не координируются. `_cleanup_keyboard` может удалить клавиатуру не с того сообщения (или с уже удалённого). `_save_msg_id` не чистит глобальный кеш.

**Риск:** `TelegramBadRequest` при попытке edit уже удалённого/отредактированного сообщения.

**Решение:** унифицировать в единую систему (global TTLCache-based — `_track_keyboard` / `_cleanup_keyboard`). Онбординг переведён на неё.

## Bug #3: menu_help не чистит FSM (MEDIUM) ✅ 2026-07-05

`menu_back` и `open_menu` вызывают `state.clear()`. `menu_help` — **нет**.

**Сценарий:** Пользователь в середине ввода траты (FSM `AddExpense.waiting_for_amount`) → жмёт Help → Help-сообщение с инлайн-кнопками → жмёт одну из них → хендлер этой кнопки может триггернуть не то состояние.

**Решение:** добавить `state.clear()` в `menu_help`.

## Bug #4: menu_settings не чистит FSM (MEDIUM) ✅ 2026-07-05

`menu_settings` не вызывает `state.clear()`. Пользователь в середине онбординга может зайти в настройки, состояние сохраняется.

**Сценарий:** Онбординг → нажал не туда → Settings → кнопка «Назад» ведёт обратно в прерванный онбординг (ок, но неочевидно). Либо жмёт другую кнопку в настройках с ожиданием другого FSM.

**Решение:** добавить `state.clear()` в `menu_settings`.

## Bug #5: cancel удаляет сообщение для reset-состояний (MEDIUM) ✅ 2026-07-05

`cancel` handler:
- Для `CriticalReset` / `FreshStart` → `callback.message.delete()` (сообщение **удаляется**)
- Для всех остальных состояний → `callback.message.edit_text()` (сообщение **редактируется** в меню)

**Последствия:**
1. Несогласованный UX: в одном месте пропадает сообщение, в другом — остаётся
2. `_last_keyboard` всё ещё хранит ID удалённого сообщения → следующий `_cleanup_keyboard` пытается edit удалённого → `TelegramBadRequest`

**Решение:** заменён `delete()` на `edit_text()` с контекстным текстом (CANCEL_CRITICAL_RESET / CANCEL_FRESH_START) + ReplyKeyboard под SIMPLE_CHECK. `_last_keyboard` теперь обновляется через middleware — TelegramBadRequest устранён.

## Bug #7: Вечерний flow — молчаливое удаление + бесконтрольный FSM (MEDIUM)

**7а. Молчаливое удаление сообщений пользователя:**
`handle_evening_expense` делает `message.delete()` для каждого сообщения пользователя. Единственный фидбек — редактирование контейнера. Пользователь может не заметить.

**7б. FSM создаётся через StorageKey напрямую:**
`send_evening_teaser` создаёт `FSMContext` через `StorageKey(bot_id=bot.id, chat_id=tg_id, user_id=tg_id)`, без проверки, не находится ли пользователь уже в другом FSM-состоянии.

**Решение:** проверять текущее состояние перед установкой вечернего FSM.

## Bug #8: dup_middleware.record() response_text = "" (LOW)

`dup_middleware.record()` всегда вызывается с `response_text=""`. В `DuplicateMiddleware.__call__()` есть проверка:
```python
if last.get("response_text"):
    # перепослать последний ответ вместо повторной обработки
```
Она никогда не срабатывает, т.к. `response_text` всегда пустая строка (falsy).

**Последствие:** защита от повторной обработки одного и того же `message_id` сломана (но на практике не критично, т.к. Telegram редко шлёт ретраи).

**Решение:** передавать реальный текст ответа в `record()`.
